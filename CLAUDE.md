# CLAUDE.md

Контекст для будущих сессий Claude Code в этом репозитории.

## Что это за проект

Репозиторий с постановочными документами для инструмента **«Rewriter Tool»** —
внутреннего инструмента редакции портала UNUM (theunum.io), который должен
ежесуточно выдавать на сайт целевое количество переписанных (AI-рерайт)
новостей по темам, заданным в редакционной политике, с обязательным
просмотром человеком (rewriter) и публикацией по кнопке **Publish**.

Сейчас репозиторий — **только документация**, кода нет. ТЗ, стайл-гайд и
реестр источников зафиксированы как базовые версии (2026-07-31); план
реализации по фазам составлен (`docs/План_Реализации_MVP.md`). 2026-08-01
оба документа расширены по заметкам заказчика об обогащении данных,
правках рерайтера, эволюции промпта, SEO/тегах и микросервисной
архитектуре (`docs/Заметки_Обогащение_Правки_Промпт.md`) — ТЗ теперь v0.4,
план v0.2; архитектура v0.3 не пересматривалась, только дополнена. Не
начинать писать код, пока пользователь явно не проревьюит и не одобрит
именно план реализации (следующий чек-пойнт, а не ТЗ — ТЗ уже
зафиксировано).

  рабочий черновик, ~26 источников подтверждены, ~16 нужно live-проверить,

  **Архитектурное решение**: НЕ один адаптер на источник — 1 универсальный
  `RssConnector` (конфигурируемый, покрывает большинство) + 6 отдельных
  `ApiConnector` только для Уровня 2 (CryptoPanic/CoinGecko/CoinMarketCap/
  CryptoCompare/Messari/LunarCrush, у каждого своя авторизация и формат) +
  список источников без найденного RSS/API — добавлять по одному по мере
  того, как для них находится реальный способ забора (не в MVP).
  Важные риски, замеченные при исследовании: у Reuters нет надёжного
  публичного RSS (нужно платно/точечно вручную); у LunarCrush в 2026 похоже
  нет полноценного бесплатного тира для продакшена — проверить перед тем,
  как закладывать в MVP; агрегаторы (CryptoCompare/Messari/CryptoPanic)
  будут давать статьи, уже забранные напрямую с Tier 1 — это ожидаемо и
  используется для кросс-верификации (§2.1 политики), а не как баг.

## Зафиксированные решения по скоупу (не переспрашивать)

Получены от пользователя при составлении и первых двух раундах ревью ТЗ
(актуально на v0.3) — считать заданными, пока пользователь их явно не
изменит:

- **Publish (статья) в MVP — чисто внутренний.** Кнопка Publish переводит
  статус материала в `published` в собственной БД инструмента. Реального
  вызова сайта/CMS для **публикации текста статьи** в MVP нет. `Publish
  Adapter` остаётся абстракцией на будущее (для реальной интеграции), но
  её MVP-реализация — no-op/внутренний переход статуса.
  **Уточнение 2026-08-01 (заметки заказчика, ТЗ §4.19):** это правило не
  распространяется на **Tag/Category** — справочник тегов/категорий живёт
  на theunum.io как мастер-система, и на Approve инструмент **реально**
  вызывает theunum.io (`CreateTag`/`EnsureCategory`, dedupe), чтобы
  записать на Draft настоящие id до публикации статьи. Это осознанное,
  единственное исключение из «no-op» — сама публикация текста статьи
  остаётся no-op, как и было.
- **LLM — через OpenRouter, только free-модели.** 3 API-ключа, хранятся в
  `.env`. Переключение между моделями **не нужно писать вручную** — у
  OpenRouter есть встроенный параметр `models` (массив ID моделей по
  приоритету): при ошибке (rate limit/модерация/контекст/даунтайм) он сам
  переключается на следующую модель в списке
  ([источник](https://openrouter.ai/docs/guides/routing/model-fallbacks)).
  Наша логика (Rotation Manager) нужна только для переключения **между 3
  ключами**, когда весь список моделей под текущим ключом исчерпан. Точный
  перечень free-моделей (`:free`) — техническая деталь, уточняется перед
  реализацией (см. открытые вопросы).
- **Стек — Python.** Весь пайплайн и backend на Python; для UI по
  умолчанию предложен Python-first вариант (FastAPI + Jinja2/HTMX), чтобы не
  вводить отдельный JS-стек — см. ТЗ §6.3 для деталей и альтернатив.
- **KPI — мягкий, 100 ± 10 в сутки** (90–110), а не жёсткий минимум и не
  жёсткий потолок. Часовой пояс отсчёта суток для MVP **игнорируется**
  (используется обычный календарный день системы, без привязки к UTC+3
  из §15.2 политики).
- **Языковой охват — двуязычный, оба языка публикуются.** Источники —
  англоязычные и русскоязычные (кластеризация по событию должна работать
  кросс-язык). Рерайт делается на **английском** (основная аудитория
  англоязычная), плюс **русский перевод** того же черновика. Оба текста
  показываются rewriter-у рядом для ревью, и **оба публикуются на сайт одним
  нажатием Publish** (не только RU для внутреннего ревью — RU-версия тоже
  идёт на сайт). Значит RU-текст должен полностью соответствовать тем же
  стандартам качества, что и EN, а не быть «черновым для проверки смысла».
- **Целевая CMS для будущей реальной интеграции — theunum.io.** В MVP
  Publish Adapter всё равно no-op (см. выше), но когда дойдём до реальной
  интеграции — это будет сайт theunum.io, а не другая площадка.
- **SSO — нужен, но не в MVP.** Доступ в итоге должен идти через SSO с
  существующей системой аккаунтов редакции UNUM; в MVP — отдельные локальные
  учётки, интеграция с SSO — пост-MVP задача.
- **Workflow одобрения — одноэтапный для MVP.** Rewriter сам просматривает
  AI-черновик (EN + RU перевод), правит и публикует. Осознанное упрощение
  §6.4 политики (финальное одобрение гл. редактора); двухэтапный вариант и
  «эскалация на доп. проверку» — не реализуются в MVP, но модель статусов не
  должна их блокировать в будущем.
- **Скоуп MVP — полный пайплайн**: мониторинг источников (RSS/API, EN+RU) →
  кросс-языковая дедупликация → AI-рерайт на EN + перевод на RU → compliance-
  проверка → очередь на ревью → публикация (внутренний статус). Не только UI
  поверх готовых черновиков.
- **Бюджет на LLM не требуется отдельно** — используются только free-модели
  OpenRouter, стоимость по построению нулевая; вместо бюджета нужен
  мониторинг лимитов/ротации (см. выше).
- **Кросс-языковая дедупликация нужна уже в MVP** — подтверждено. EN- и
  RU-источники об одном событии должны объединяться в один News Cluster
  (ТЗ §4.2), а не давать два независимых черновика.
- **Хостинг окружения разработки — Railway** (railway.com). Managed
  PostgreSQL + сервисы в одном Railway-проекте, секреты — через Railway
  Variables. Продовое окружение, если будет отличаться от dev, — вопрос
  пост-MVP.
  **Уточнение 2026-08-01:** сервисов теперь **три**, не два —
  `api`, `worker` и **`rewrite`** (отдельный Python-микросервис
  `scribely-rewrite`, только gRPC, с Фазы 0, ТЗ §6.6). Rewrite-логика,
  LLM-ключи и ключи keyword-провайдеров изолированы в `rewrite`;
  `api`/`worker` — gRPC-клиенты к нему, без общего импорта бизнес-логики
  LLM.
- **Тестовый Rewriter на этапе MVP — реальный сотрудник редакции UNUM**, не
  сам пользователь-заказчик и не условная роль. Следствие: даже в MVP нужен
  настоящий логин/пароль конкретного человека в БД (ТЗ §3), не заглушка
  «для себя».
- **ТЗ (v0.3 база от 2026-07-31, v0.4 дополнение от 2026-08-01), стайл-гайд
  и реестр источников зафиксированы как базовые версии** — дальнейшие
  правки только по ходу разработки, не пересмотр архитектурных решений.
  Следующий чек-пойнт для ревью — `docs/План_Реализации_MVP.md`.
- **Правила рерайта и стиля зафиксированы** в отдельном документе
  `docs/Правила_Рерайта_и_Стиля_Черновик.md` — это основа системного промпта
  Rewrite Orchestrator. Ключевое: не использовать «ё», не использовать
  «Таким образом» (только «Так,»), простой некликбейтный заголовок по
  правилам Дзена, обязательное упоминание изданий-источников в тексте, ~2000
  символов на весь материал в 3 небольших абзацах (это — допущение, требует
  подтверждения). Плюс мои редакторские добавления: активный залог, короткие
  предложения, без канцеляризмов и ИИ-штампов («важно отметить», «таким
  образом» и т.п.), цифры с контекстом, без эмодзи/кликбейта.

## Конвенции репозитория

- Документы (ТЗ, CLAUDE.md, стайл-гайд) пишутся на русском языке — рабочий
  язык команды и первоисточник (редполитика). Сами публикуемые новости —
  на английском и на русском (обе версии публикуются, см. выше).
- Не создавать код/имплементацию, пока пользователь явно не подтвердит план
  реализации после ревью ТЗ.
- Диаграммы — Mermaid прямо в markdown (контекстная и компонентная — C4-стиль
  через `flowchart`, т.к. это надёжно рендерится везде, включая GitHub/VSCode).
