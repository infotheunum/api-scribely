# CLAUDE.md

Контекст для будущих сессий Claude Code в этом репозитории.

## Проект

**Rewriter Tool** — внутренний инструмент редакции UNUM (theunum.io):
ежесуточно собирает инфоповоды по темам редполитики, делает AI-рерайт
(EN + RU), прогоняет через compliance-проверки и отдаёт сотруднику
редакции (rewriter) на ревью и публикацию по кнопке **Publish**.

ТЗ v0.4, План реализации v0.2, стайл-гайд и реестр источников
зафиксированы как база — не пересматривать без явного запроса
пользователя. План одобрен 2026-08-03, реализация идёт по фазам (см.
«Статус реализации» ниже).

## Зафиксированные решения (не переспрашивать)

- **Publish** в MVP — только внутренний статус `published`, без вызова
  сайта/CMS. Исключение — **Tag/Category**: на Approve инструмент реально
  вызывает theunum.io (`CreateTag`/`EnsureCategory`, ТЗ §4.19).
- **LLM** — OpenRouter, только free-модели, 3 ключа в `.env`. Ротацию
  моделей делает встроенный параметр OpenRouter `models`; наша логика
  (Rotation Manager) — только переключение между 3 ключами (ТЗ §4.5).
- **Стек** — Python везде, включая UI (FastAPI + Jinja2/HTMX по умолчанию).
- **KPI** — мягкий таргет 100 ± 10/сутки, без учёта часового пояса.
- **Языки** — источники EN+RU, кросс-языковая дедупликация обязательна
  уже в MVP. Рерайт на английском + русский перевод; **обе версии
  публикуются** одним Publish, к RU те же стандарты качества, что и к EN.
- Целевая CMS для будущей реальной интеграции — theunum.io.
- SSO нужен, но не в MVP (локальные учётки).
- Одобрение — одноэтапное (сам rewriter публикует), без эскалации на
  главного редактора.
- Скоуп MVP — полный пайплайн (ingestion → dedup → rewrite → compliance →
  review → publish), не только UI поверх готовых черновиков.
- Бюджет на LLM не нужен — только free-модели.
- Хостинг разработки — Railway: managed Postgres + **3 сервиса**
  (`api`, `worker`, `rewrite`). `rewrite` (`scribely-rewrite`) — отдельный
  Python-микросервис, только gRPC, с Фазы 0 (ТЗ §6.6); LLM-ключи и
  keyword-provider ключи изолированы в нём, `api`/`worker` — просто
  gRPC-клиенты, без общего импорта бизнес-логики.
- Тестовый Rewriter — реальный сотрудник редакции UNUM, не сам заказчик;
  нужен настоящий логин/пароль в БД, не заглушка.

## Статус реализации

**Фаза 0 (Фундамент) — готова, задеплоена на Railway и полностью
верифицирована (2026-08-03).** Структура репозитория,
`proto/scribely/rewrite/v1/rewrite.proto` (все 11 методов ТЗ §6.6),
`libs/db/models.py` (все 17 таблиц ТЗ §6.4 + первая Alembic-миграция,
автоприменяется на каждом деплое `api` перед стартом), `libs/common`
(trace_id, internal service-token, логирование), `services/rewrite`
(gRPC health + все методы на проводе, осознанно возвращают
`UNIMPLEMENTED` — логика в Фазе 4), `services/api` (health,
`/health/rewrite`, `/auth/login`+`/auth/me` на JWT/argon2),
`services/worker` (health + gRPC-клиент; ingestion — Фаза 1).

Проект на Railway: workspace **Unum**, project `api-scribely`
(id `00d2f337-c04d-41f4-8232-b9c72e2662da`), 3 сервиса (`api-scribely`,
`worker`, `rewrite` — первый исторически не переименован в `api`, токен
проекта не даёт прав на rename) + managed Postgres. Публичные домены:
`api-scribely-production.up.railway.app`,
`worker-production-2bbc.up.railway.app` (у `rewrite` домена нет и не
должно быть — только приватная сеть). Все `/health` и `/health/rewrite`
отвечают 200 на реальных URL.

**Три реальных бага, пойманы только на живом деплое (локально/в тестах
не проявлялись) — см. commit-историю за 2026-08-03 для деталей:**
1. `libs/common/grpc_client.py` использовал `grpc_health`, а зависимость
   `grpcio-health-checking` была объявлена только у `rewrite`, не у
   `libs` — поймано локальной сборкой Docker-образа `rewrite` (там нет
   `unum-api`/`unum-worker`, только `unum-libs`).
2. `libs/common/tracing.py` тянул `starlette` ради `TraceIdMiddleware`,
   хотя `rewrite` — чисто gRPC-сервис без HTTP-зависимостей вообще (ТЗ
   §6.6). Разнёс на `tracing.py` (протокол-агностичное ядро) и новый
   `common/http_middleware.py` (Starlette-часть, только для api/worker).
3. Managed Postgres от Railway отдаёт `DATABASE_URL` без указания
   драйвера (`postgresql://...`), SQLAlchemy в этом случае берёт
   `psycopg2` по умолчанию — которого нигде не установлено (everywhere
   `psycopg` v3). Нормализация — в `CommonSettings` (валидатор pydantic),
   один раз для всех потребителей.
4. `RewriteSettings.port` — Railway на каждый сервис сам подставляет
   `PORT` (под публичный HTTP-прокси), а pydantic-settings матчит env-
   переменные по имени поля регистронезависимо: поле тихо получало
   значение Railway `PORT` вместо нашего 50051. Переименовано в
   `grpc_port`; заодно убрано мёртвое одноимённое поле у `api`/`worker`
   (они всё равно биндятся на shell `$PORT` напрямую в Dockerfile CMD).
5. gRPC-сервер `rewrite` слушал `0.0.0.0` (только IPv4) — приватная сеть
   Railway (`*.railway.internal`, через которую api/worker ходят в
   rewrite) IPv6-only. Переключено на `[::]` (dual-stack на Linux).

Осознанные отклонения от дерева каталогов в Плане §2: один общий
`libs/grpc_gen/` вместо дублирующего `services/rewrite/app/generated/`
(план в прозе ниже дерева так и описывает); устанавливаемое имя
Python-пакета `app/` у каждого сервиса переименовано на
`api_app`/`worker_app`/`rewrite_app` (каталоги на диске не менялись) —
иначе три сервиса с одинаковым именем пакета `app` перекрывали бы друг
друга на общем dev-интерпретере и при общем `pytest` с корня репозитория.

**Фаза 1 (Ingestion/RSS) — готова, локально верифицирована на реальных
данных (2026-08-03).** `RssConnector` (`services/worker/app/ingestion/
rss_connector.py`, `feedparser`+`httpx`, конфигурируемый — не адаптер на
источник), circuit breaker (5 подряд неудач → пауза на час), fallback
полного текста для Tier 1 через `libs/common/fulltext.py`
(`httpx`+`trafilatura`, используется и RSS-фоллбэком, и ручным inject —
общая инфраструктура, не бизнес-логика конкретного коннектора), поллинг
на `APScheduler` (тик 60с, каждый `Source` опрашивается по своему
`poll_interval_seconds`). `scripts/seed_sources.py` — 9 источников из
реестра, живо перепроверенных `curl` 2026-08-03 (не просто скопированных
как ✅): CoinDesk/Cointelegraph/Decrypt/CryptoSlate/Bitcoin Magazine/
BeInCrypto/NewsBTC (все Tier 1, EN) + **BeInCrypto RU**
(`ru.beincrypto.com/feed` — найден и подтверждён в процессе, реестр не
содержал точного URL; закрывает требование Плана §4 про RU-источник для
демо кросс-языковой дедупликации) + SEC (Tier 3, регулятор). Bloomberg
Crypto (пример из Плана §3) при живой проверке оказался мёртв (404) —
понижен до 🔴 в реестре, заменён на этот набор.

Локальная демонстрация (не на Railway, реальный интернет): 210
RawItem за первый цикл поллинга, оба языка (EN+RU, кириллица цела),
fallback-догрузка полного текста отработала именно там, где лента даёт
только summary (в среднем 3.2k символов на fallback-статью против 12k у
источников с `content:encoded`). Circuit breaker и идемпотентность —
покрыты тестами (`services/worker/tests/test_poller.py`,
`test_circuit_breaker.py`), не отдельным ручным прогоном — 5 подряд
реальных фейлов означало бы держать сессию открытой лишний час без
дополнительной пользы поверх теста.

Ручной inject URL (ТЗ §4.1) — **`POST /ingestion/inject` в `api`**, не в
`services/worker/app/ingestion/` как буквально написано в дереве Плана
§2. Причина: auth/roles живут в `api` (ТЗ §6.3), а `api`/`worker` — два
независимых устанавливаемых пакета без общей бизнес-логики между собой
(только через `libs/`); эндпоинт, требующий роль Rewriter/Admin, не мог
бы переиспользовать код из `worker_app` без нарушения этой границы.
Идемпотентен по самому URL (как источник истины вместо guid), всегда
тянет полный текст (нет RSS-summary, из которого можно было бы не
дотягивать).
