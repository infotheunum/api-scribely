# Технический реестр источников для модуля сбора новостей (Ingestion)

**Статус:** v0.1 — зафиксировано как базовая версия (2026-07-31); статусы
✅/🟡/🔴 по конкретным источникам продолжают уточняться в фоне по ходу
разработки (это штатный процесс, см. П9 редполитики)
**Проект:** UNUM_news_100
**Назначение:** этот документ — то самое «техническое приложение», о котором
говорит редполитика в П9 («Технический реестр точных адресов RSS-лент и
API-эндпоинтов… ведется и обновляется техническим отделом отдельно от
настоящей политики»). Здесь для каждого источника из
[Редакционная_Политика_UNUM_Глобальная_версия.md](Редакционная_Политика_UNUM_Глобальная_версия.md)
(Приложение 1) зафиксировано: точный способ забора данных, эндпоинт,
авторизация, лимиты и заметки для парсинга — чтобы можно было сразу писать
код Ingestion Service (ТЗ §4.1, §6.3).

> **Как читать колонку «Проверка»:**
> ✅ — URL/эндпоинт подтверждён из официального источника (документация
> вендора, официальная RSS-страница).
> 🟡 — найден через вторичные источники (агрегаторы фидов, форумы,
> сторонние RSS-каталоги) — правдоподобно, но не подтверждено напрямую с
> сайта источника, проверить перед продакшеном.
> 🔴 — точный адрес не найден в этом раунде исследования — нужна ручная
> проверка/реверс-инжиниринг перед тем, как включать источник в код.
>
> Ни одна запись здесь не должна считаться окончательной без быстрой
> live-проверки (`curl`/браузер) непосредственно перед реализацией —
> сайты меняют платформу, добавляют защиту от ботов и т.д.

## 0. Рекомендация по архитектуре сборщика (адаптеры vs один модуль)

**Короткий ответ: НЕ один адаптер на источник.** Из ~67 источников
подавляющее большинство — это обычные RSS/Atom-ленты, различающиеся только
URL и парой параметров. Писать 60+ почти одинаковых модулей — это чистое
дублирование и кошмар поддержки (правило «конфигурация, а не код» уже
зафиксировано в ТЗ §5 «Расширяемость реестра источников»).

Предлагается **3 типа коннекторов**, а не N:

1. **`RssConnector` (универсальный, конфигурируемый)** — покрывает ~45–50 из
   67 источников. Один класс на Python (`feedparser` + `httpx`), на вход —
   запись из реестра (URL ленты, язык, tier, category-mapping). Никакого
   кода под конкретный сайт не пишется — только строка в конфиге/БД
   `Source`.
   - Параметры на источник: `feed_url`, `language`, `poll_interval`,
     `category_hint`, `user_agent` (некоторые сайты блокируют дефолтный UA
     библиотек — иногда достаточно представиться как браузер).
   - Крайние случаи (не отдельный коннектор, а **флаги** на том же
     `RssConnector`): сайт требует специфичный `User-Agent`/заголовки
     (Cloudflare-защита) — обрабатывается общим retry/backoff + ротацией UA,
     не отдельным кодом.

2. **`ApiConnector` — по одному классу на вендора, только для Уровня 2**
   (CryptoPanic, CoinGecko, CoinMarketCap, CryptoCompare, Messari,
   LunarCrush) — **6 классов**, не 45. Здесь один класс на источник
   оправдан: у каждого своя авторизация, пагинация и формат ответа,
   конфигом это не унифицировать. Плюс отдельные адаптеры бирж, где вместо
   RSS используется их announcement API (Bybit — см. Уровень 5).

3. **`ManualWatchConnector` / список «требует уточнения»** — источники, где
   в этом исследовании не нашёлся стабильный публичный RSS/API (Reuters,
   ESMA, FCA, MAS, FATF, IOSCO, Tether, Chainwire и др. — см. пометки 🔴
   ниже). Их **не стоит** пытаться с ходу заскрапить хрупким кастомным
   парсером HTML для каждого. Рекомендация: (а) для MVP взять только
   источники с ✅/🟡 статусом — этого уже с запасом хватает на 90–110/сутки
   по расчётам П8 политики; (б) источники 🔴 добавлять по одному по мере
   того, как для них найден реальный способ забора, отдельной задачей
   технического отдела (что явно предусмотрено П9 политики — реестр
   пересматривается и обновляется).

Итого кода: **1 универсальный RSS-коннектор + 6 API-адаптеров + реестр
конфигураций** — вместо 67 модулей. Это и есть предполагаемая реализация
`Ingestion Service` из ТЗ §6.3.

## 8. Общие технические заметки для реализации `RssConnector`

- Использовать `feedparser` (Python) — он терпим к небольшим огрехам в XML,
  которые часто встречаются у мелких изданий.
- Часть сайтов (за Cloudflare) блокирует дефолтный User-Agent библиотек —
  закладывать возможность задать кастомный `User-Agent` per-source в
  конфиге, а не хардкодить.
- RSS обычно даёт только summary, не полный текст — для рерайта (ТЗ §4.4)
  этого обычно достаточно (мы и так не берём текст дословно), но если нужен
  полный текст первоисточника для верификации фактов (§2.1 политики) —
  закладывать fallback-догрузку страницы по ссылке из `<link>`.
- Дедуп по `guid`/`link` внутри одного источника — обязателен на уровне
  `RssConnector` (не путать с кросс-источниковой дедупликацией кластеров,
  ТЗ §4.2 — это следующий, более сложный уровень).
- Для источников-агрегаторов новостей (CryptoCompare, Messari, CryptoPanic)
  — высокий риск получить статьи, которые мы и так уже забрали напрямую с
  Tier 1 — это нормально и даже полезно для дедупликации/верификации (§2.1
  политики: «один и тот же инфоповод… используется для перекрёстной
  верификации»), но нужно не публиковать их как отдельные, самостоятельные
  кластеры.
- Хранить `language` на уровне `Source` (не угадывать по контенту) — для
  корректной работы кросс-языковой дедупликации (ТЗ §4.2).
